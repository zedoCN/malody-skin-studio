# Malody 4.3.7 native UIS rendering findings

APK: `/Users/zedo/Downloads/malody-4-3-7.apk`, previously verified SHA-256 `7b6f5650481f6b1e04ebe8eec93f18c2205521522f94da3f129cfb0c37044138`.
Binary: `lib/arm64-v8a/libmalodycpp.so` in that APK. Addresses below are ELF virtual addresses; `.text` and `.rodata` have identical file offset/VA in this binary. This document describes statically proven instruction behavior; function names below are semantic labels assigned during analysis, not surviving symbols. llvm-objdump labels with long unrelated C++ names are nearest exported symbols and must NOT be treated as actual function names.

## Reproduce

```
python3 -m venv /tmp/uis437-venv
/tmp/uis437-venv/bin/pip install capstone pyelftools
/tmp/uis437-venv/bin/python scripts/uis437_native.py \
  /path/to/malody-4-3-7.apk /tmp/uis437-native
```

The script checks the exact APK SHA-256, extracts only its ARM64 library, and writes `uis-arm64.asm`, `uis-xrefs.txt`, `hash-xrefs.txt`, and `functions.txt` under the output directory. Its FDE function boundaries come from `.eh_frame`; straight-line `adrp/add` tracking can produce stale-register false positives, so all cited addresses were manually checked against disassembly. Property names are reconstructed from immediate BKDR hash constants.

## Main native entry points

- `0x2cce04`: 64-bit BKDR hash, `h = h*131 + unsigned char`. Known property/directive strings are compiled as immediate hashes, explaining why searching plain strings misses them.
- `0x2d1f18..0x2d721c`: script parser; hashes dispatch directives and properties. `@include` and `@includex` branch through `0x2d3f44 -> 0x2d7228` (file/script read wrapper). `@includex` additionally sets a flag at `0x2d3f84`; its full observable semantics remain unproven.
- `0x2cd2b8`: dimension expression evaluator. `w2=1` selects context+0x14 (width), `w2=0` selects context+0x18 (height). Bare number multiplies context+0x8 (`@unit` factor), `%` multiplies selected axis/100, `w` multiplies context+0xc/1280, `px` leaves value unscaled. Operators +/-, named definitions, and `$` appear in this evaluator.
- `0x2cb770`: component factory; queries property ID100 (type), switch table at `.rodata 0x9e3b28`.
- `0x2ca090`: common initial node properties application.
- `0x2c9e70`: anchor application.
- `0x2ca418`: image settings wrapper, calls `0x2c9c40`, then common properties `0x2ca090`.
- `0x2ca99c`: animation/action binding. Initial properties below must not be applied as rounding to every animation interpolation frame.

## Proven scalar/geometry differences from editor

### fsize

- Hash compare at 0x2d5438 matches `fsize`.
- Branch `0x2d6ed0`: set property ID140; call dimension evaluator 0x2cd2b8 with w2=0 (height). Thus `fsize=20`, `20px`, `5%`, `20w`, and definition expressions are not interchangeable.
- Constructors query ID140 at 0x2cb970. With value, `FCVTZS` truncates float toward zero at 0x2cb9b4 or 0x2cc3f8, then converts back to float to pass to text factory.
- Absent fsize passes literal20.0 at 0x2cc470 / 0x2cc4e4. This is NOT an expression-evaluated 20 unit default.
- Text factories 0x43fedc and 0x43ffb0 multiply by a density factor, round with FCVTAS, and apply inverse density scale. Exact glyph rasterization requires original font and density; correcting expression/default/truncation is still directly justified.
- The earlier editor implementation used `getDouble(fsize,16)` and skipped the dimensional evaluator; this has been corrected in the current tree.

### pos / rotate / opacity

All are in common initial node style. Type0 uses 0x2cb7ec ->0x2ca418->0x2ca090. Types1/2/4/5/6 join0x2cb94c->0x2ca090. Type3 each sequence frame uses0x2cb620->0x2ca418->0x2ca090.

- pos property ID20: `0x2ca354` and `0x2ca360` FRINTA round native x/y to integer with ties away from zero before virtual setter+0x88. Round native bottom-origin y before coordinate inversion; if canvas height is fractional, rounding already-inverted canvas y need not be identical.
- The editor now rounds the initial standalone `pos` on its native axes before Y inversion. Parent-relative position needs separate context mapping, and animated position interpolation remains fractional.
- rotate ID283: parser `0x2d65f8..0x2d660c` atof->float; renderer `0x2ca278` FCVTZS -> int, SCVTF back -> Vec3 z -> virtual setter+0x180. It truncates fractional angles toward zero for initial static style.
- opacity ID287: parser `0x2d665c..0x2d6678` atof * double2.55 (literal at0x2d7220), FCVT float, FCVTZS int. Common style `0x2ca334` LDRB loads low8bits then virtual setter+0x408. For valid0..100 input, editor should at least support fractional percentage and reproduce 8bit quantization. The earlier editor used integer percent/100; the current tree applies 8-bit quantization.
- Scope is initial style, NOT all subsequent animations. Cocos actions can interpolate float positions/angles.

### anchor

- Default0..8 mapping matches editor's 3x3 mapping (top-left to bottom-right when presented in top-origin UI).
- `0x2d6da4` parses comma-separated anchor tuple using atoi per component (not unit expression), stores mode=-1 and float x/y. `0x2c9e70` default branch divides x by original content width and y by original content height before anchor setter+0x128. So arbitrary pixel anchors are supported by APK. The editor now applies the proven content-size formula to plain image sprites; other renderer types still need their own original content-size mapping.

## Not recovered

Full perspective camera matrix, note hold type1/type3 drawing, per-mode handlers, glyph font rasterization, exact animated interpolation timing, and includex condition scope remain unresolved. These findings support targeted correction plus existing true-device probes; they do not prove complete renderer equivalence.

## Anchor scope and type6 priority

Anchor is handled by ID220 in common initial style: compare at `0x2ca224`, call to anchor helper `0x2ca2ac`. Thus it has the same type0..6 coverage as common pos/rotate/opacity (type3 applies to each constructed frame). Tuple `(0,0)` is the native node's bottom-left anchor; scalar `0` maps to native `(0,1)` / top-left. Explicit tuple values are pixels of the node content before its transform scale, not generally pixels of the final rendered bounding box. For a simple image with native W,H and final rendered w,h, the top-origin anchor offset is `(tupleX*w/W, (H-tupleY)*h/H)`. Native code bails out if content W or H is below1e-6 (`0x2ca088` holds this double constant). Do not translate tuple anchors through a 9-state JavaFX enum.

`type=6` needs a separate video renderer for real support: factory consumes `file` (hash branch `0x2d2c30 ->0x2d5914`, ID291), constructs VideoSprite at `0x2cbf84 ->0x2da790`, applies bit0 of toggle ID260 at `0x2cbfa0`, starts it via `0x2cbfb0 ->0x2dac18`, then runs common style. A static image renderer cannot substitute its playback/decoding/loop semantics. No `type=6` match was found in the already-extracted `/tmp/malody-437-apk/builtin-mui` and `/tmp/malody-mui-corpus` text during this pass. Recommend explicitly list it as unsupported while preserving script/file resources; defer a decoder/player until a real target sample exists. Existing work should not add a speculative empty VideoSprite wrapper.
