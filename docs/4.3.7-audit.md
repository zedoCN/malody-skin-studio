# Malody 4.3.7 UIS 校准记录

本记录区分游戏本体证据、编辑器预览实现和仍需验证的推断。分析对象是用户提供的 `malody-4-3-7.apk`，SHA-256：`7b6f5650481f6b1e04ebe8eec93f18c2205521522f94da3f129cfb0c37044138`。不把 APK 或其内置资源提交到仓库。

## 已确认

- APK 的 `classes.dex` 和 `lib/arm64-v8a/libmalodycpp.so` 都含 `4.3.7` 版本字符串。游戏核心是已剥离大部分符号的 ARM64 C++/Cocos2d 库；Java 层主要负责 Android 容器，不能用 Java 反编译器直接看到 UIS 绘制实现。
- `assets/libskin.so` 是内置资源容器，不是 ELF 动态库。它含 300 个条目；条目头和长度允许提取明文 UIS 脚本。筛出的 55 份 UIS 文本片段均可由本编辑器的文本解析器读取，但原始文件名被哈希，部分 `@include` 无法直接还原，因此这不是完整的运行时验证。
- 游戏内置 UIS 文本使用 `@apply 3d`、`@angle 45`、`@unit`、`@if phone`、`type=5` 搭配 `rect`，以及 `opacity=85`。这些是 4.3.7 实际接受的写法；它们本身没有给出投影或绘制算法。
- Emiria 5.0 原型的 `UISFactory.Setup` 将 Mac 同时标记为 `mac` 和 `windows`。编辑器保留此兼容行为；APK 内置脚本没有提供足够信息验证 4.3.7 对 Mac 的同名条件细节。
- 两份明确写有 `@version 4.3.7` 的外部皮肤在 0 ms、PC 预览中能加载，没有组件不支持的日志。修改解析器后，两份截图曾与旧版逐字节一致；去掉可确定的调试标记后，分别有约 0.14% 和 0.17% 像素变化。
- Android 开发机（`NOH_AN01`，截图 `2376×1152`）经 `adb` 安装并运行了这份 4.3.7 APK。游戏从 `/sdcard/data/malody/skin` 读取外部 `.msz`，在皮肤菜单选中后成功运行 4K 样本谱面。以设备宽高比生成编辑器截图时，赛道左右边界、判定线按键位置和右侧 HUD 的布局与真机相符。游戏画面还包含谱面的背景图、倒计时和实时 note，静态编辑器截图没有这些上下文，不能做全屏像素差判定。
- 在 4.3.7 真机上加载 30×30、九块纯色的临时 `type=5` 测试纹理：`rect=10px,10px,10px,10px`、`size=90,90`、不写 `size2` 时，输出约 139×139 设备像素，边框保持约 10 设备像素，中部被拉伸。真机顶部红／绿／蓝色块的横向范围分别是 1119–1128／1131–1244／1247–1256；编辑器按原生截图尺寸输出后的对应范围是 1116–1125／1129–1246／1250–1259。几像素的整体偏移与游戏上下留黑、画布高度不同有关。改为 `rect=5px,5px,20px,20px` 并重启游戏后，各色块的切分边界按九宫格变化。当前编辑器据此实现了无 `size2` 的九宫格路径。
- 同一素材、`rect`、`size` 在真机上逐项改变 `size2`，第二项改变了九宫格的**边框宽度**，外框仍约 139×139 像素；`0,120px` 与 `180px,120px` 的颜色范围相同，表明第一项在这一组实验中不参与切片。量取顶部纯红／纯绿／纯蓝的连续区域如下（设备像素，抗锯齿过渡带未计入）：

  | `size2` | 红 | 绿 | 蓝 |
  | --- | ---: | ---: | ---: |
  | 省略 | 9 | 108 | 9 |
  | `0,270px` | 39 | 52 | 39 |
  | `0,540px` | 19 | 88 | 19 |
  | `0,1080px` | 10 | 106 | 10 |
  | `0,120px` | 46 | 不可见 | 88 |

  边框符合 `源纹理边框像素 × 画布高度 / size2 高度` 的规则；例如 `540px` 使 10 像素边框约变为 20 像素。`120px` 时左右边框合计超过目标宽度，游戏让右切片覆盖左切片，未压缩到外框内。编辑器已按此实现。`0,540px` 的编辑器与真机纯色色块横向边界最多相差 2 像素；`0,120px` 的覆盖情形最多相差 3 像素。两者纵向仍受本设备有效画布高度差异影响。该规则只在这台设备、这张方形纹理和这组参数上校准过，其他纵横比和纹理待复测。
- 透视控制组用同一个 4.3.7 皮肤包追加九个绿色标记，位于横向 20%／50%／80%、纵向 15%／50%／85%，`zindex=50`。真机与编辑器均以 2376×1152 截图。`@apply 3d` + `@angle 1`、`28`、`40` 的标记横坐标最多相差 1.5 像素；`@angle 0` 或省略 `@angle` 的真机画面与编辑器 `30°` 的横坐标最多相差 0.5 像素，和编辑器旧 `0°` 明显不同；去掉 `@apply 3d`、仅保留 `@angle 40` 后，真机标记平面排列。解析器据此增加 `@apply 3d` 开关与零角度默认 30° 的规则。
- 真机与编辑器的标记纵坐标满足约 `y_真机 = 22 + 0.96 × y_编辑器`（本设备截图，三个高度的残差约 1–2 像素）。因此直接用整屏像素差会把游戏上下留黑／有效绘制区域差异误判成透视公式误差。这个经验映射仅用于当前设备的截图分析，未加入通用渲染公式。
- 选用 `Sterelogue` 的 4K Beginner 谱面（含 `endbeat` 的长按 note）与 `Thirteen-Malody-4k-5.msz` 皮肤，在 4.3.7 真机连续截图。该皮肤 `tex=BLUE.png`、`tex5=GREEN.png`、`tex2=noteL.png`、`tex3=noteT.png`；游戏长按头部确实显示绿色，普通 note 显示蓝色，长按身体和尾部为灰色。编辑器此前把示例长按头部也画成蓝色，现改为有 `tex5` 时使用它，并保留判定线处普通 note 的 `tex`。这只校准了素材选择和示例外观，没有将真实谱面时序引入预览。

## 当前编辑器与原版的差距

| 项目 | 当前状态 | 证据边界 |
| --- | --- | --- |
| `@unit`、百分比、`w`、批量名称、定义和条件 | 已结合 Emiria 5.0 原型及真实 4.x 样本修正 | 632 份外部 `.mui` 文本与 55 份 APK 内置 UIS 片段通过文本解析；不等于每项渲染语义正确 |
| `@apply 3d` 与 `@angle` 透视 | 已按真机处理开关和零角度默认 30°；保留 2024 年经验多项式 | 九点标记在 1°、28°、40° 的横坐标误差不超过 1.5 设备像素；0° 与 30° 对应；尚未从 C++ 库恢复相机与投影公式，也未覆盖所有角度、纵横比及组件类型 |
| 自定义组件 `type=5` | 已实现 `rect`、`size` 与 `size2` 的九宫格预览；`size2` 高度缩放边框，超出外框时保留原版切片覆盖顺序 | 方形测试纹理在真机上验证了无 `size2`、`0,120px`、`0,270px`、`0,540px`、`0,1080px`；第一项与更多设备、纹理的行为仍需复测 |
| note 的 hold `type=2` | 示例长按头部优先使用 `tex5`，普通 note 仍使用 `tex`；身体、尾部继续按已有路径绘制 | 真机实际谱面确认了头部颜色；身体、尾部的几何和真实长按时序尚未逐帧定量校准 |
| note 的 hold `type=1`、`type=3` | 渲染分支未完整实现 | 当前 `NoteComponentRenderer` 的分支为空或缺失身体绘制；不能声称 hold 预览与游戏一致 |
| 文本 `fsize` | 保留现有直接数值渲染 | Emiria 5.0 原型按画布高度和 `@unit` 缩放；4.3.7 尚无真机字号对照，不能直接套用 5.0 规则 |
| `.mui` 保存 | 原文模型保留编码、注释、未知属性和各行行尾；代码编辑器保存时恢复源文件一致的 CRLF／CR 行尾 | 原始文件混用行尾时，代码编辑器仍可能统一行尾；原文模型的无修改往返已由真实样本字节级验证 |
| note 的静态示例 | 编辑器在判定线绘制示例 note | 同时刻游戏依谱面播放，未必有 note；此差异不是皮肤几何解析错误，但说明固定帧预览尚非游戏运行时模拟 |
| key／通用帧动画 | 现在跟随预览时间选帧 | 已消除系统时钟导致的固定帧不稳定；具体游戏触发时机尚未比对 |
| 得分、note、bar 的彩色辅助标记 | 已移除明显的调试绘制 | 不属于皮肤素材；去除后需用游戏画面作最终视觉验收 |

Emiria 历史 UIS 源码属于 5.0.0 原型，可提供格式线索，不能代替 4.3.7 的运行时实现。下一步应复测九宫格在更多纹理和设备上的行为，并校准 hold 绘制及更多角度／纵横比下的投影。

## 真机复测方法

仓库中的 `scripts/skin437_probe.py` 在生成、打包、推送和截图时只依赖 Python 标准库与 `adb`；自动量取截图标记的 `compare` 子命令另需 `ffmpeg`。它从**同一份** `.msz` 继承脚本和资源，再附加测试节点；这样不会把不同版本的 `.mui` 与素材混装。测试纹理和节点可重建，APK、样本包和游戏截图不提交仓库。

```sh
python3 scripts/skin437_probe.py panel --output /tmp/panel.png
python3 scripts/skin437_probe.py scale9 --size2 0,540px --output /tmp/scale9-540.mui
python3 scripts/skin437_probe.py build --base '/path/to/4.3.7-skin.msz' --append /tmp/scale9-540.mui --asset /tmp/panel.png --output /tmp/Codex-Scale9.msz
python3 scripts/skin437_probe.py push --serial DEVICE_SERIAL /tmp/Codex-Scale9.msz
python3 scripts/skin437_probe.py capture --serial DEVICE_SERIAL --output /tmp/game-437.png
python3 scripts/skin437_probe.py measure-panel --image /tmp/game-437.png --roi 1000,740,400,250 --output /tmp/game-panel.json
./mvnw javafx:run '-Djavafx.args=--snapshot /path/to/extracted/script-key-4K.mui /tmp/editor-437.png 0 ANDROID:2376x1152'
```

在游戏“设置 → 图形 → 使用皮肤”中选测试包，再进 4K 谱面。**游戏会缓存 UIS 脚本**：修改已解包的 `.mui` 后只点谱面“重试”仍会看到旧布局；重新启动游戏再比较。`capture` 会在截图旁保存 `.json`（游戏版本、选中的皮肤、截图尺寸与 SHA-256）和最新游戏日志。`measure-panel` 需要 `ffmpeg`，`--roi` 指定只覆盖测试色块的区域，避免其他界面颜色进入统计。调试 `size2` 时每次只改一个参数；曾将不同版本脚本和素材混装导致游戏报缺 `RED.png`，该结果不能用于判断九宫格实现。

透视复测可用同一个源包分别生成 `0`、`1`、`40` 度测试节点；`--no-apply` 可生成只写 `@angle` 的平面对照组，`--no-angle` 可验证默认 30°。截图前检查 `capture` 的 `skin_selection`，避免皮肤列表多选或再次点击已选项目造成错误对照；`compare` 对空选／多选的截图会拒绝比较。

```sh
python3 scripts/skin437_probe.py perspective --angle 40 --output /tmp/angle-40.mui --asset-output /tmp/perspective-marker.png
python3 scripts/skin437_probe.py build --base '/path/to/4.3.7-skin.msz' --append /tmp/angle-40.mui --asset /tmp/perspective-marker.png --output /tmp/Codex-Perspective-40.msz
python3 scripts/skin437_probe.py compare --editor /tmp/editor-40.png --device /tmp/game-40.png --output /tmp/compare-40.json
```
